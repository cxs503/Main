# 质量门 v1（QUALITY BAR）—— owner 2026-10-25「需要严格质量把控，要不然会形成一堆垃圾」

定位：所有常设线（expand/benchmark/operator/campaign）推送与合并前的统一硬规则。
门本身也要能失败（R1 适用于质量门自身）。违反任何一条 = 阻断推送，非降级警告。

## 六条硬规则

**R1 门必须能失败（杀伤性）**
新增或修改任何验收门/基准判据，必须附 mutation 探针证明该门在故意破坏时会失败
（假参考曲线/破坏守恒/欠解析/关物理项/采样盲区五类探针至少其一）。探针随套件
常驻（@mutation 标记）。无探针的门=未验收的门，不得作为交付依据。
先例：TensorSPH #10（恒真判据修复）、TensorLBM #396→#398（假参考教训）。

**R2 参考数据必须可溯源**
基准参考只允许三类：解析解（附推导/出处）、实验数字化（附文献+数字化脚本）、
高可信独立实现（附交叉对照证据）。禁止自生成曲线自证闭环。参考数据变更必须
走独立 PR，不得与实现变更混提。

**R3 硬缺陷一票否决**
以下任一成立，无论其他项得分/套件多绿，一律 FAIL：
- 关键守恒关系失效（质量/动量/能量账本不闭合且无披露）；
- 参考数据不真实（R2 违例）；
- 核心物理项未实际参与计算（配置布尔≠方程路径，含「为过门禁禁用物理」——
  SI-4 铁证锚：禁重力保 0.0e+00 残差门）；
- 规模/语义与 goal 声明不符（semantic_gate 三判据）。

**R4 基线红记账，新增红阻断**
套件以 main 基线红集合为账本（.base_reds 快照）：新增红=阻断推送；基线红只
允许减少不允许增加。CI 长期红的库必须先清零存量红（修实现/lint，禁改断言），
红 CI 库的一切「绿」皆不可信。

**R5 失败保留（honest-FAIL 不可覆盖）**
FAIL 判决及其证据不可被后续「修绿」commit 覆盖或删除；修复必须以新实验+根因
说明另立条目（append-only 判决史）。先例：mp_dambreak 4/4 FAIL 披露文化。

**R6 无报告=未收官（报告是交付物，不是附属品）**
每个终态 mission 必须有对应平台进展报告（论文级、图文并茂：物理表述+
流场/应力云图+曲线+审计+局限，见「平台报告论文级常设标准」）才算收官；
FAIL mission 必须有失败分析条目（honest-FAIL 与 R5 同源）。合并报告允许
（一篇覆盖多 mission），但须在 title/summary/tags 中机判可溯（m<id>）。
机器账本：`tools/ops/report_ledger.py`（cron 对账 owed/failed_owed →
`agent_work/quality/report_debt.json`）；operator 班次巡检第 6 步消费，
按剧本派「报告补账」mission。豁免：值班班次与补账 mission 自身。
先例：2026-10-23 12:07（id=55）后断更两日、三常设线 28 单无报告——
owner 2026-10-25「原先要求图文并茂的发表论文级质量的报告」。

## 执行机制（落地路径）
1. tools/ops/quality_gate.py（PL-SEM-3 交付）：输入分支/PR → 五规则逐条机判
   → PASS/FAIL+理由；收割线阻断式接入（工具自身异常=fail-open 登记人工位，
   但判定结果永不 fail-open）。
2. PR 开出时自动发机器质量评论（五规则逐条+证据链接），owner 合并前必读。
3. QUAL 审计线对存量做抽查回溯（m306 起四样本）。
4. 质量门自身的杀伤性：R1 同样约束 quality_gate.py（交付须含对质量门的
   mutation 测试：喂坏工件必须 FAIL、喂好工件必须 PASS）。
5. R6 由 report_ledger.py 机器对账（账本可假阴性不可假阳性——宁可多派
   补账，不可漏记）；报告缺图=未达标（图片上传后 200 image/png 亲验）。
