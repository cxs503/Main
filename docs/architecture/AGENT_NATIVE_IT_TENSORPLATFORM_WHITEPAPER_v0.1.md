# Agent-Native IT 技术栈与 TensorPlatform 演进架构白皮书

**版本：** v0.1（讨论稿）  
**日期：** 2026-10-23  
**定位：** 面向 Agent 自主科研基础设施的技术架构与演进路线  
**项目背景：** TensorPlatform 与 Tensor 系列科学计算项目

> 本文是架构白皮书初稿，用于统一方向、定义术语和指导工程实施。它不是对当前系统所有能力均已实现的声明。涉及仓库的具体代码状态、部署状态、性能和测试结果，仍需以对应 GitHub 仓库、CI 记录和真实部署验证为准。

## 摘要

当前主流 IT 基础设施大多围绕人类使用者设计：人通过图形界面、命令行、文档和流程操作软件，软件执行明确指令，人在任务之间负责判断、协调和恢复。大模型与 Agent 的出现，使软件系统开始拥有理解目标、规划行动、调用工具、生成代码和评估结果的能力。这带来一个不同于“给传统软件加一个 AI 聊天入口”的工程命题：如果 Agent 成为大量数字工作的主要执行者，IT 系统是否应从底层接口、软件工程、任务运行时、数据治理和安全机制等方面，重新组织其服务方式？

本白皮书提出 **Agent-native（面向 Agent 原生设计）** 的概念：系统不再把 Agent 仅视为 GUI 背后的自动化脚本，而是将其视为具有身份、上下文、任务目标和受控行动能力的软件主体。Agent-native 系统应提供机器可发现的能力、结构化契约、持久化任务状态、可恢复执行、可验证产物、可追溯证据和强制执行的权限边界，同时保留适合人类监督、审查和决策的界面。

对于 TensorPlatform，建议以“面向 Agent 作为科研主体的黑灯工厂式科研基础设施”为长期定位，采用渐进式技术路线：复用 Linux、容器、Git、CI、现有科学计算语言与集群资源；优先建设统一的科研能力契约、任务生命周期、Agent 运行时、验证与溯源体系；再逐步形成跨求解器编排、自动实验、自动修复与知识沉淀闭环。短期不建议先发明通用编程语言或操作系统，而应以真实科研任务验证架构。

**核心结论：Agent-native 的关键差异不在于模型本身，而在于围绕 Agent 的可行动性、持续性、可验证性和可治理性重新组织软件与基础设施。**

## 1. 背景与问题定义

### 1.1 Human-first 系统的隐含假设

大量传统软件默认以下条件成立：

- 用户可以阅读界面、文档和提示，理解功能的使用顺序；
- 用户能够记住任务上下文，并在多个工具之间人工搬运信息；
- 用户会判断错误是否严重、决定重试或修改参数；
- 用户发起一次操作后，会主动查看状态并决定下一步；
- 用户可以通过经验补足接口中未表达的语义和约束。

这些假设对人类工作流通常合理，但对持续运行的 Agent 不够可靠。Agent 需要明确的输入输出、状态语义、错误分类、权限边界和验收条件；否则系统会依赖脆弱的页面操作、提示词约定或隐式知识。

### 1.2 Agent-native 的定义与核心属性

Agent-native 系统是一类将 Agent 视为一等执行主体，并围绕其能力发现、目标执行、状态持久化、结果验证、资源治理和人类监督进行设计的软件与基础设施系统。它不意味着 GUI、传统语言或人工审批会消失，而是意味着机器可操作接口、任务状态和验证证据成为核心设计要素。

四项核心属性：

1. **可行动（Actionable）**：能力可发现、可调用、可组合，参数与副作用明确。
2. **可持续（Persistent）**：任务状态、会话引用、检查点和待办事项能够持久化，进程退出不等于任务遗失。
3. **可验证（Verifiable）**：任务完成依赖测试、约束和证据，而不只依赖模型的文字判断。
4. **可治理（Governable）**：身份、权限、预算、审批、审计和停止机制由系统强制执行。

## 2. 设计原则

### 2.1 人机双界面，而不是取消人类界面

系统应同时提供面向人的 GUI（目标设定、状态监督、结果浏览、审查和审批）和面向 Agent 的 API/CLI/协议（能力发现、结构化调用、状态查询和产物获取）。GUI 不应成为 Agent 自动化的唯一入口；Agent 接口也不能取代人类需要的可视化与审计。

### 2.2 复用成熟底座，创新集中于编排与契约

优先复用 Linux、容器、数据库、对象存储、Git、CI、工作流和集群调度生态。TensorPlatform 的差异化应集中在科研语义、任务生命周期、能力契约、验证证据和 Agent 持续执行机制上，而不是重复建设通用操作系统、版本控制或调度器。

### 2.3 模型可替换，任务与上下文不应被模型绑定

模型是可替换的推理后端。任务身份、研究目标、状态、产物、审计记录和可恢复上下文应由平台管理。一次模型调用结束、一个 Agent 进程退出或模型 API 配额不足，都不应自动导致科研任务丢失。

### 2.4 “完成”必须有验收依据

系统应区分推理调用完成、一次 Agent 执行阶段完成、任务达到验收标准，以及任务失败/取消/转交人工。对科学计算，验收可包括数值稳定性、守恒误差、基准曲线偏差、网格收敛、实验对比、输出文件完整性和可重复性等。

### 2.5 真实状态优先于展示状态

界面显示的排队、运行、完成、失败、验证通过等状态，必须由真实任务记录、进程或调度器状态、产物检查和验证结果驱动。不得以 mock 数据、静态演示或未经运行的预期结果冒充真实计算。

## 3. Agent-native IT 技术栈

建议将技术栈划分为八层。该分层是目标架构，不代表所有层当前均已实现。

| 层级 | 目标职责 | 关键能力 |
|---|---|---|
| L8 目标与治理 | 定义目标、约束、风险和责任边界 | 目标管理、审批、策略、审计 |
| L7 Agent 运行时 | 维持任务持续推进 | 会话引用、上下文恢复、事件触发、队列、重试、交接 |
| L6 能力接口 | 让 Agent 发现和调用工具 | API/CLI、能力目录、类型化输入输出、错误语义 |
| L5 软件工程 | 生成、修改、构建和验证软件 | Git、分支/PR、CI、静态分析、测试、构建溯源 |
| L4 数据与知识 | 管理输入、产物和经验 | 数据模式、元数据、版本、血缘、检索、实验记录 |
| L3 领域应用 | 承载可组合的科学计算能力 | 求解器、前后处理、耦合模块、基准算例 |
| L2 执行与编排 | 运行作业并管理资源 | 容器、任务调度、CPU/GPU、隔离、检查点 |
| L1 基础设施 | 提供计算与存储 | Linux、网络、服务器、集群、GPU、对象存储 |

Agent 不会改变 CPU、GPU 或网络的物理原理，但会改变资源的申请、调度、观察、恢复和计费方式。最先需要升级的通常是层与层之间的接口、任务状态模型和自动验证机制。

### 3.1 统一任务对象

一个科研任务至少应包含唯一标识、目标、输入数据、参数和单位、所需能力与版本、资源预算、超时、优先级、安全策略、当前状态、执行尝试、检查点、事件记录、输出产物、验证报告、验收结论及溯源信息。

建议使用显式状态机，例如：

`CREATED → QUEUED → RUNNING → VALIDATING → SUCCEEDED`

并支持暂停、等待重试、失败、取消和需要人工处理等状态。状态转换必须可审计，并避免重复执行造成不一致副作用。

## 4. 编程语言与软件工程方式的演进

### 4.1 不应急于寻找“唯一的 Agent 语言”

未来更可能是多语言协作，而非单一语言取代所有现有语言：

- C/C++、Fortran、CUDA、Rust 等继续承担性能敏感、底层或高可靠组件；
- Python、PyTorch 等继续承担数值算法、实验编排、数据处理和 AI 工作负载；
- JSON Schema、OpenAPI、类型系统及领域描述语言用于表达调用契约和任务规格；
- 工作流定义与状态机用于表达长周期任务的依赖、重试和分支；
- 测试、静态分析和数值验证负责为 Agent 生成的代码提供证据。

### 4.2 从“写代码”扩展为“声明目标—生成实现—验证结果”

推荐的 Agent 软件工程闭环：

1. 解析需求和约束；
2. 检索相关代码、文档、历史问题和基准；
3. 形成可审查的实施计划；
4. 修改代码并生成测试；
5. 执行静态检查、单元测试和集成测试；
6. 运行基准算例并分析偏差；
7. 生成变更摘要、证据和风险说明；
8. 经策略允许后创建 PR 或交付部署；
9. 观察真实运行结果，失败时恢复或回滚。

代码生成只是其中一步。没有测试、运行和验收闭环的代码生成，不应被视为完整的软件工程自动化。

### 4.3 Agent Capability Contract（能力契约）

建议建立跨项目统一的能力描述规范，至少包含：

1. **Identity**：名称、版本、所属项目和兼容性；
2. **Inputs**：参数模式、类型、单位、范围和前置条件；
3. **Execution**：调用方式、依赖、资源需求、超时与副作用；
4. **Outputs**：输出结构、文件格式、字段含义和单位；
5. **Validation**：测试集、基准版本、误差阈值和证据；
6. **Lifecycle**：排队、运行、暂停、恢复、失败、取消和完成；
7. **Security**：所需权限、可执行操作、预算与审批条件；
8. **Provenance**：代码版本、输入数据、环境、日志和产物来源。

该契约是领域语义层，不应简单等同于 MCP 或某一种 API。MCP、HTTP API、CLI 可以是不同的传输和调用方式，能力契约则定义这项科研能力是什么、如何正确使用、怎样判定结果有效。

## 5. Agent 运行时与持续执行

### 5.1 运行时必须与单一模型进程解耦

系统应分离以下概念：

- **任务**：需要达到的目标和验收条件；
- **会话**：某个 Agent 的交互与上下文载体；
- **执行尝试**：一次具体的运行过程；
- **模型调用**：一次推理请求；
- **工作进程**：实际执行命令或代码的进程；
- **产物**：执行生成的文件、数据、报告和证据。

这些对象有关联，但生命周期不应完全绑定。

### 5.2 持续推进机制

持续执行不是无限循环调用模型，而是由事件驱动的受控状态机推动：

1. 事件进入：新目标、定时触发、作业结束、PR 更新、验证失败或资源可用；
2. 调度器读取持久化任务状态；
3. 根据策略唤醒适当的 Agent；
4. Agent 选择下一步行动并调用工具；
5. 执行结果、日志、产物和状态写回平台；
6. 评估是否继续、重试、暂停、结束或升级给人；
7. 下一次触发由队列、调度器或事件系统负责。

应实现幂等键、超时、重试上限、退避策略、死信处理、并发锁和取消机制，防止重复事件引起重复计算或破坏性操作。

### 5.3 上下文与知识管理

上下文不能只存在于单个模型窗口。建议区分长期项目知识、任务状态、执行轨迹和当前模型调用所需的有限运行时上下文。上下文恢复应依赖结构化状态与检索，而不是简单保存并无限拼接历史对话。

## 6. 科学计算与自主科研的特殊要求

通用 Agent 平台与科研 Agent 平台的关键差别，在于科研结果必须满足物理、数学和实验约束。

### 6.1 科研闭环

`目标与假设 → 数值方案 → 算例构建 → 计算执行 → 结果验证 → 对比分析 → 结论与报告 → 下一轮实验`

每个阶段都需要可追溯的输入和输出。系统可以自动提出后续实验，但是否执行高成本、不可逆或风险较高的动作，应由策略和权限决定。

### 6.2 多层验证

- 软件级：类型检查、静态分析、单元测试、接口测试；
- 数值级：守恒、稳定性、收敛性、误差估计；
- 基准级：与解析解、公开 benchmark 或已验证结果比较；
- 物理级：边界条件、量纲、物理约束和合理性检查；
- 工程级：资源消耗、性能、可恢复性和产物完整性；
- 可复现级：版本、参数、数据和运行环境可追溯。

“程序成功退出”只证明执行过程未以已知错误结束，不等于科学结果正确。

### 6.3 Tensor 项目体系的建议分工

以下是基于项目定位的架构建议，不代表已核验所有仓库当前实现细节：

- **TensorPlatform**：平台层，承载 Agent 任务组织、能力目录、运行状态、权限治理、数据与产物追溯、UI/API 和持续调度；
- **TensorLBM**：格子 Boltzmann 方法相关求解能力及其 benchmark；
- **TensorFEM**：有限元相关求解能力、结构问题和相应验证案例；
- **TensorDEM**：离散元、键合颗粒、接触与断裂相关能力及 benchmark；
- **TensorSPH**：平滑粒子流体动力学能力与液滴入水等验证案例；
- **TensorBEM**：边界元相关数值能力及其基准测试；
- **TensorPhysics**：适合跨求解器复用的物理模型、单位、材料关系和公共物理能力；具体边界应通过代码盘点确定，避免机械搬迁。

项目是否已支持某项能力，应由仓库代码、测试、运行记录和真实产物证明。平台应保留“已声明、可调用、测试通过、基准通过、部署验证通过”等不同状态，避免把规划能力显示为已交付能力。

## 7. 数据、知识与科研产物

科研产物应包含结构化元数据：产物类型、格式、大小和校验和；生成任务与执行尝试；软件版本、Git 提交、参数和运行环境；数据来源、许可和敏感级别；关联验证结果；与前序输入及后续分析之间的血缘关系。

可复用知识应包括代码和测试、能力契约、benchmark 规格与参考数据、故障案例和修复记录、数值方法说明与适用边界、经过验证的工作流模板、运行数据和性能基线。知识库不能把 Agent 的猜测直接当成事实，条目应注明来源、验证状态、适用版本和可信度。

## 8. 安全、可靠性与治理

Agent 具备行动能力后，必须使用系统级约束，而不能只依赖提示词。建议的最低安全基线：

- 每个 Agent、服务和任务具有可区分身份；
- 默认最小权限，凭证短期化，禁止将秘密写入日志；
- 文件系统、网络和执行环境按任务隔离；
- CPU、GPU、存储、并发和费用均有预算；
- 危险操作、外部发布、生产部署和数据删除按风险要求审批；
- 所有关键动作具备审计记录；
- 支持停止、取消、超时、回滚和凭证撤销；
- 对模型输出、代码、依赖和外部输入保持不信任边界；
- 任务失败时保留现场、日志和可恢复状态。

建议按风险分级授权：只读检索、沙箱计算、创建分支/PR、部署测试、生产变更等操作分别定义权限和审批规则。

## 9. TensorPlatform 目标架构

建议采用逻辑分层，而不是让单个 Agent 进程承担所有职责。核心组件包括：

1. **用户与治理界面**：目标输入、审批、任务观察、结果浏览和审计；
2. **Agent Gateway**：统一认证、会话路由、工具调用策略和限流；
3. **任务与事件中心**：任务状态机、队列、事件、重试和调度；
4. **Agent Runtime Adapter**：适配不同模型和 Agent 执行器，管理调用与上下文引用；
5. **Capability Registry**：登记项目能力、版本、契约和验证状态；
6. **Execution Backend**：容器、服务器、集群和科学计算作业执行；
7. **Data & Artifact Service**：输入、日志、结果、报告、检查点和产物索引；
8. **Validation Service**：测试、benchmark、指标比较和验收；
9. **Policy & Audit Service**：权限、预算、审批、审计和风险控制；
10. **Observability**：平台健康度、Agent 运行健康度和科研任务进度。

关键边界：模型提供推理，不拥有任务的唯一持久化状态；Agent 决策下一步，但不能绕过平台权限与预算策略；求解器负责数值计算，不自行宣称平台任务已验收；验证服务提供证据，验收规则决定任务状态；UI 展示真实状态；资源调度和执行后端可替换，任务与产物模型保持稳定。

## 10. 实施路线图

### 阶段 0：现状盘点与基线冻结

交付：对 TensorPlatform 和各 Tensor 仓库进行代码级盘点；标记能力“已实现、部分实现、仅规划、未验证”；梳理现有 UI、API、Agent 接入、任务执行、数据管理和部署方式；选定一个真实端到端科研任务作为验收基线；记录现有测试、部署和失败情况。

退出条件：每项结论均有仓库、代码、测试或真实运行证据；没有证据的内容明确标为待核验。

### 阶段 1：统一能力契约与真实任务执行

交付：第一版能力契约规范；至少一个求解器接入标准化任务接口；真实任务提交、状态查询、结果下载和日志查看；自动化 benchmark 与结果验收；UI 状态完全来自真实后端。

退出条件：Agent 能独立提交一个真实计算任务，任务状态可追踪，产物存在且通过指定验证。

### 阶段 2：持久化任务与可恢复 Agent Runtime

交付：任务、会话、执行尝试和模型调用的分离模型；事件触发、任务队列、超时、重试和取消；中断恢复与幂等控制；可替换的模型/Agent 后端；权限、预算和审计的最小可用版本。

退出条件：停止某个 Agent 进程后，平台仍保留任务状态，并能按策略继续、恢复或转交人工。

### 阶段 3：跨求解器科研工作流

交付：多能力组合和依赖图；统一实验记录、数据血缘和产物目录；跨求解器验证与比较；失败分类、自动重试和有限范围内的参数调整。

退出条件：至少一个多阶段科研工作流从目标输入走到可验证报告，不依赖人工逐步点击推进。

### 阶段 4：受控的软件自我改进闭环

交付：Agent 读取问题、生成变更、执行测试、运行 benchmark；自动创建分支和 PR，附带测试证据和风险摘要；根据策略执行部署测试；生产变更保留人工审批和回滚机制。

退出条件：一次真实缺陷修复或能力扩展能够从问题记录走到 PR、测试证据和部署验证，全流程可审计。

### 阶段 5：面向多领域扩展

在统一契约、运行时、治理和验证机制稳定后，再扩展到更多求解器、实验设备、数据科学、材料、流体、结构、生物和其他 AI4S 领域。扩展应复用核心基础设施，不应让每个领域形成一套独立 Agent 平台。

## 11. 指标与验收

不能仅用 Agent 数量、代码行数或模型调用量衡量平台进展。建议关注：

| 指标类别 | 建议指标 |
|---|---|
| 自主执行 | 无人工逐步干预完成的端到端任务比例 |
| 可靠性 | 任务成功率、恢复成功率、重复执行副作用率 |
| 科学有效性 | benchmark 通过率、误差、守恒偏差、可复现率 |
| 工程质量 | 测试覆盖、回归缺陷率、PR 验证完整度 |
| 效率 | 从目标到有效产物的时间、人工干预次数 |
| 资源利用 | CPU/GPU 利用率、排队时间、单位有效任务成本 |
| 可追溯性 | 产物具备完整来源和验证证据的比例 |
| 安全性 | 越权阻断率、审计覆盖率、预算违规次数 |

每项指标应定义分母、采集方式、统计周期和基线，避免以主观估计代替测量。

## 12. 风险与反模式

### 12.1 反模式

- 只增加聊天框，却没有可用的结构化接口；
- 用无限循环和定时调用代替可靠任务调度；
- 把上下文只保存在某个模型窗口或进程内存；
- 把 MCP 工具数量当作 Agent-native 程度；
- 让模型自行判定科研结果正确，而没有独立验证；
- 将规划中的能力在 UI 中显示为已经可用；
- 每个项目各自设计一套不兼容的任务和产物格式；
- 过早重写操作系统或发明通用编程语言；
- 给 Agent 过大权限，依靠提示词而不是强制策略限制风险。

### 12.2 主要风险及应对

- **模型不确定性**：以工具约束、测试和独立验收降低风险；
- **长任务中断**：持久化状态、检查点和恢复流程；
- **重复事件**：幂等键、锁和可审计的状态转换；
- **接口漂移**：能力契约版本化、兼容性检查和回归测试；
- **科研误判**：独立 benchmark、物理约束和实验数据对照；
- **成本失控**：预算、超时、并发限制和成本可观测性；
- **安全风险**：最小权限、沙箱、短期凭证和人工审批；
- **过度平台化**：以真实任务和验收标准推动建设，避免为抽象而抽象。

## 13. 近期优先级建议

建议优先做以下五件事：

1. **建立真实状态清单**：逐仓库检查代码、测试、CI、部署与运行结果，区分事实和规划；
2. **定义能力契约 v1**：选择一个代表性求解器和 benchmark 试点，而非一次性改造所有仓库；
3. **建立真实任务闭环**：从任务创建、执行、日志、产物到验证结果全链路打通；
4. **拆分任务状态与 Agent 进程**：保证模型切换、进程退出或 API 配额变化不会丢失任务；
5. **构建自动验收门禁**：没有真实测试证据的任务不能被标记为科学验证通过。

第一个端到端示范应选择现有 benchmark 中边界清晰、耗时可控、结果易于比较的算例。液滴入水、边界元基准或其他案例都可以候选，但最终应以仓库当前实现、运行成本和验收数据为依据。

## 14. 结论

Agent-native IT 不是“用 AI 替代人操作电脑”的简单自动化，而是围绕新的软件执行主体重构接口、状态、验证和治理机制。它既需要大模型，也更需要可靠的软件工程、任务运行时、数据系统、计算执行环境和安全控制。

TensorPlatform 的长期竞争力不应建立在某一个模型或编码 Agent 上，而应建立在以下平台资产之上：

- 跨项目统一、机器可理解的科研能力契约；
- 与模型解耦的任务状态和可恢复执行机制；
- 可组合的科学计算能力与真实 benchmark；
- 自动化验证、可复现运行和产物溯源；
- 强制执行的权限、预算和审计体系；
- 能从真实科研任务中持续积累的工程与领域知识。

**总体策略：不先重造底层技术，而是先建立 Agent-native 的能力与执行层；不以演示界面作为完成标准，而以真实任务、可验证产物和可恢复运行作为验收标准；不把模型视为平台本身，而把模型视为平台可以替换的推理能力。**

当这些机制形成闭环后，TensorPlatform 才有可能从一个连接 AI 工具与科学软件的平台，逐步发展为面向 Agent 自主科研的基础设施。

## 附录 B：术语表

- **Agent-native**：围绕 Agent 作为一等执行主体进行设计。
- **能力契约（Capability Contract）**：对能力的语义、输入输出、执行条件、验证和权限作出的机器可读声明。
- **任务（Task）**：具有目标、状态、预算和验收条件的持久化工作单元。
- **会话（Session）**：承载 Agent 交互与上下文的逻辑单元。
- **执行尝试（Attempt）**：任务的一次实际执行过程。
- **产物（Artifact）**：任务生成的代码、数据、图表、日志或报告。
- **溯源（Provenance）**：将产物与代码、数据、环境、参数和执行过程关联起来。
- **黑灯科研工厂**：在明确的目标、权限与验收规则下，能够持续自动推进科研任务、生成可验证产物并在必要时升级人工决策的基础设施模式。
