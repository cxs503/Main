## 总体判断

## 方向 A：SDAA 性能基线（A1/A2/A3）

### ① 致命伤

**无绝对致命伤，但 A2 的"安静窗协议"存在硬件控制权假设未验证。**

提案要求 A2 独占 1 卡、用 `teco-smi` 做 quiet-gate（SPE-Util ≤10%、温度 ≤60°C、功耗 ≤80W），但**未证明 agent 有权限强制其他进程退出或阻止调度器分配新任务到该卡**。如果 quiet-gate 只是"观测"而非"控制"，则 CV ≤2% 的门在共租环境下几乎必然触发 `BASELINE_INVALID`——这不算 FAIL，但也不算 PASS，等于**该 mission 没有可达成路径**。

**验证建议**：在 A2 判据中增加一条前置检查——`teco-smi` 能否列出当前卡上运行的进程 PID？若能，quiet-gate 可裁；若不能，A2 应降级为"观测性基线"并修改判据。

### ② 被低估的风险

- **A1 的"统计量裁决自由度"实验设计依赖 `m397` 的 5 次连跑数据**，但提案 §6 已承认"热降频/共租/内存泄漏/长任务调度排队四种可能没有区分证据"。A1 若只做描述性统计而不做因果分离，产出的"协议"只是对已有噪声的拟合，**不具备外推性**。
- **A3 的回读端点**（`/api/v1/baselines/read`）假设平台已有该 API 或能快速开发，但提案未给出端点 schema 或现有 API 的探查结果。若端点不存在，A3 的交付物将退化为文档，**不满足"真功能开发单"要求**。

### ③ 判据是否机器可裁

| 判据 | 可裁性 | 备注 |
|---|---|---|
| A1: CV ≤2% / 漂移 ≤5% | ✅ 完全可裁 | 数值比较，无歧义 |
| A1: median vs mean 偏差 ≤3% | ✅ 完全可裁 | 数值比较 |
| A2: quiet-gate 三阈值 | ✅ 可裁（前提是 teico-smi 可读） | 若 teico-smi 输出格式变化需适配 |
| A2: BASELINE_INVALID 触发条件 | ⚠️ 半可裁 | "连续 3 次 quiet-gate 不通过"可裁，但"不通过"的原因分类（共租/热降频/其他）不可自动区分 |
| A3: 回读值与写入值 sha256 一致 | ✅ 完全可裁 | 哈希比较 |

**结论**：A 方向判据整体机器可裁性良好，但 A2 的 BASELINE_INVALID 路径需要明确"不触发 BASELINE_INVALID 才算 PASS"还是"触发 BASELINE_INVALID 但原因可归类也算 PASS"。当前文本模糊。

### ④ 预算/墙钟是否现实

- A1（0 卡，离线统计）：140 调用/5400 s **充裕**，预计 <15 min 可完成。
- A2（1 卡独占）：140 调用/5400 s **紧张但可行**，前提是 quiet-gate 能快速通过。若共租严重导致反复重试，5400 s 可能不够完成 5 次有效测量。
- A3（0 卡）：140 调用/5400 s **充裕**。

**非阻断**：A2 的墙钟风险可通过增加 quiet-gate 超时后的快速失败路径缓解。

### ⑤ 缺失项

- A2 未定义"安静窗"的**最大等待时间**。如果卡一直不空闲，mission 是等 5400 s 还是提前放弃？
- A3 未说明回读端点是新建还是复用现有 API。若是新建，需要后端开发时间，**不在 140 调用预算内**。

## 方向 B：张量后端矩阵脚本化（B1/B2/B3）

### ① 致命伤

**B2 的"设备探针"判据存在逻辑循环风险。**

B2 要求验证"计算是否真的在卡上"，判据包括 `torch_file_ratio ≥30%` 和 `SHELL_ONLY` 门。但 `torch_file_ratio` 只是文件级 grep（提案 §1.2 已承认"不等于算在卡上"），而 `SHELL_ONLY` 门的定义是"import torch 但无 `.cuda()`/`.to(device)` 调用"——这仍然只是**静态分析**，不是运行时验证。

**真正的"算在卡上"验证需要**：运行时检查 tensor 的 `.device` 属性，或用 `teco-smi` 观测计算期间卡的 SPE-Util 跃升。B2 判据未包含这一层，因此**即使 B2 PASS，也不能证明计算在卡上**。

### ② 被低估的风险

- **B1 扩到 10 库的脚本化**：提案未列出 10 个库的具体名单。若包含不存在的库或无 `requirements.txt` 的库，脚本会静默跳过或报错，导致"10 库"变成"实际探测 N 库"，**判据被稀释**。
- **B3 的 3D 湍流算例**：提案说"与 B3 不复用同算例"（指 M8 的 3D 球体阻力），但未说明 B3 用什么算例。若 B3 需要新算例，5400 s 内完成网格生成+求解+后处理**极紧张**。

### ③ 判据是否机器可裁

| 判据 | 可裁性 | 备注 |
|---|---|---|
| B1: 10 库 torch_file_ratio 表 | ✅ 可裁 | 脚本输出 JSON 即可 |
| B2: torch_file_ratio ≥30% | ✅ 可裁 | 但物理意义弱（见①） |
| B2: SHELL_ONLY 门 | ✅ 可裁（AST 分析） | 但只能证"没显式调 cuda"，不能证"算在卡上" |
| B3: 3D 湍流精度 vs 文献 | ⚠️ 半可裁 | 文献值需人工注入；若文献有多个值取哪个？ |

**结论**：B 方向判据在形式上可裁，但**物理有效性不足**。B2 应增加运行时设备检查（如 `tensor.device` 断言或 `teco-smi` 观测）。

### ④ 预算/墙钟是否现实

- B1（0 卡）：140 调用/5400 s **充裕**。
- B2（2 库串行/并行）：140 调用/5400 s **紧张**，每个库需 clone + 依赖安装 + AST 分析 + 运行时探测，5400 s 对两个库可能不够。
- B3（1 卡）：140 调用/5400 s **极紧张**，3D 湍流求解本身可能就需要数小时。

**非阻断**：B2/B3 的墙钟风险可通过缩小探测范围（B2 只查关键文件、B3 用简化算例）缓解。

### ⑤ 缺失项

- B1 未定义"10 库"的具体名单和来源（是 `/root/tensor-ecosystem/` 下所有目录？还是另有清单？）。
- B3 未指定 3D 湍流算例的几何、Re 数、网格规模，**无法预估墙钟**。

## 方向 C：自由面守恒与多相精度（C1/C2/C3）

### ① 致命伤

**C1 的"根因分析"任务在 140 调用/5400 s 预算内几乎不可能完成。**

根因分析需要：① 复现问题（跑 dambreak3d）；② 修改代码/参数做消融实验；③ 定位到具体代码行或算法步骤；④ 写出根因报告。5400 s 可能只够跑 1-2 次完整模拟（取决于网格规模），**不足以做系统性消融**。

提案 §4 的放弃条件写"预算内既无根因又无可失败实验 → 关单"，这实际上承认了**高概率 FAIL**。但 C1 是 C2/C3 的前置依赖，C1 FAIL 会导致 C2/C3 全部阻塞。

### ② 被低估的风险

- **C2 的等价性判据依赖 C1**：提案说"C2 必须在 C1 之后"，但若 C1 FAIL（只交根因不交修复），C2 的"等价性"比较的是**两个都有 bug 的版本**，这没有物理意义。
- **C3 的 Laplace 定律验证**：提案要求 `Δp·R/σ` vs 理论值误差 ≤3%，但伪势/相场模型的 `σ` 本身是**通过界面厚度和相互作用参数间接定义的**，不是直接输入。若界面分辨率不足（<3 格），`Δp·R/σ` 的系统误差可能远超 3%，**这不是调参能解决的**。

### ③ 判据是否机器可裁

| 判据 | 可裁性 | 备注 |
|---|---|---|
| C1: 给出根因（代码行/算法步骤） | ⚠️ 半可裁 | "根因"的充分性需人工判断；可裁的是"是否给出了具体代码位置" |
| C1: 可失败实验设计 | ✅ 可裁 | 实验设计文档存在即可 |
| C2: sha256 全等或 L2 ≤1e-6 | ✅ 完全可裁 | 哈希/范数比较 |
| C2: 记录首个分歧 step | ✅ 完全可裁 | 数值比较 |
| C3: Δp·R/σ vs 理论 ≤3% | ✅ 完全可裁 | 数值比较 |
| C3: 两网格加密误差降幅符合阶数 | ⚠️ 半可裁 | "符合阶数"需定义容差（如 GCI 的 Fs=1.25） |

**结论**：C 方向判据在数值比较层面可裁，但 C1 的"根因"和 C3 的"阶数符合"需要更精确的定义。

### ④ 预算/墙钟是否现实

- C1（0 卡）：140 调用/5400 s **极紧张**，根因分析通常需要多次迭代。
- C2（1 卡）：140 调用/5400 s **紧张**，100 step 的 3D 模拟可能接近上限。
- C3（0 卡）：140 调用/5400 s **可行**，Laplace 定律验证通常用 2D/小 3D 算例。

**非阻断**：C1 应明确"根因"的最小交付标准（如"定位到 free-surface 处理的具体函数"即可，不要求修复）。

### ⑤ 缺失项

- C1 未定义 dambreak3d 的网格规模、时间步数、物理参数，**无法预估单次模拟耗时**。
- C3 未说明与历史 m24/m25/m52 的对照表中，若历史数据缺失如何处理。

## 方向 D：DEM-FEM 耦合（D1/D2）

### ① 致命伤

**D1 的"真 FEM Hertz"存在环境依赖风险，且降级路径的判据与原始目标不等价。**

提案 §6 已承认"`m404` 记录 TensorFEM 在当次工作区不可用，而今天仓库存在——二者必有一方是环境问题"。D1 的第一步是"裁决这个矛盾"，但如果 TensorFEM 的依赖（如特定版本的 torch、scipy、petsc4py）在当前环境中不满足，D1 会在环境安装阶段消耗大量时间，**可能 5400 s 内无法进入物理计算**。

降级路径（梁挠度 + DEM 单颗粒）虽然可行，但**与原始 Hertz 接触的物理目标完全不同**——梁挠度是线弹性小变形，Hertz 接触是非线性大变形接触。降级后 PASS 不等于原始目标 PASS。

### ② 被低估的风险

- **D2 的耦合接口 schema**：提案要求"两库往返序列化位等"，但 TensorFEM 和 TensorDEM 可能使用不同的序列化格式（pickle vs JSON vs msgpack），**位等在跨格式场景下无意义**。
- **D1 的 4 条门**（指数 1.5±0.05 / 刚度 ≤3% / 能量漂移 ≤1% / 网格加密刚度变化 <5%）中，能量漂移 ≤1% 对显式时间积分**极难满足**（DEM 的 dt≈1.69e-5 意味着 10000 step 才有 0.169 s 物理时间，能量累积误差可能远超 1%）。

### ③ 判据是否机器可裁

| 判据 | 可裁性 | 备注 |
|---|---|---|
| D1: TensorFEM git sha + 依赖安装证据 | ✅ 完全可裁 | 命令输出比对 |
| D1: 梁挠度 ε≤3% vs Euler-Bernoulli | ✅ 完全可裁 | 解析解已知 |
| D1: DEM 单颗粒 Hertz 指数 1.5±0.05 | ✅ 完全可裁 | 幂律拟合 |
| D1: 刚度 ≤3% | ✅ 完全可裁 | 数值比较 |
| D1: 能量漂移 ≤1% | ✅ 可裁 | 但物理上可能不可达（见②） |
| D1: 网格加密刚度变化 <5% | ✅ 完全可裁 | 数值比较 |
| D2: schema 自校验通过 | ✅ 完全可裁 | jsonschema 验证 |
| D2: 单步能量交换守恒 ≤1e-3 | ✅ 完全可裁 | 数值比较 |

**结论**：D 方向判据全部机器可裁，但部分判据（能量漂移 ≤1%）在物理上可能不可达，需要调整容差或明确"不可达时记 WITHHELD"。

### ④ 预算/墙钟是否现实

- D1（0 卡）：140 调用/5400 s **紧张**，环境安装可能消耗 30-60 min。
- D2（0 卡）：140 调用/5400 s **充裕**，schema 定义和单步测试不需要大量计算。

**非阻断**：D1 应增加环境预检查步骤（`pip install --dry-run` 或 `conda env export` 比对），若依赖不满足则快速 FAIL，不浪费墙钟。

### ⑤ 缺失项

- D1 未说明 TensorFEM 的**具体版本/分支**，不同版本的 API 可能不兼容。
- D2 未定义"单步"的具体含义（是 DEM 的一个时间步？还是 FEM 的一个 Newton 迭代？还是耦合的一个宏步？）。

## 跨方向共性问题

### 1. 依赖链的级联失败风险

```
C1 → C2 → C3
B1 → B2 → B3
D1 → D2
A1 → A2 → A3
```

若 C1 FAIL，C2/C3 全部阻塞；若 B1 的 10 库名单不全，B2/B3 的输入不完整。**提案未定义"上游 FAIL 时下游如何处理"**——是跳过、降级、还是也 FAIL？

### 2. 预算帽的"每单 140/5400"是否合理

提案所有 mission 都用相同的 140 调用/5400 s 预算，但任务复杂度差异巨大：
- A1（离线统计）：预计 <15 min
- C1（根因分析）：可能需要数小时
- B3（3D 湍流）：可能需要数小时

**统一预算导致简单任务浪费、复杂任务不足**。建议按任务类型分级预算。

### 3. "真功能开发单"的认定

owner 指令要求"每波必须含 ≥2 条真功能开发单（交付=代码+测试+文档，端到端可用）"。本提案中：
- A3 的回读端点：若是新建 API，算真功能
- B1 的脚本化：若是可复用脚本，算真功能
- D2 的 schema：若是可复用的接口定义，算真功能

但提案**未明确标注哪些 mission 是"真功能开发单"**，需要议事会裁决。

## 修正建议

### 建议 1：增加"上游 FAIL 时下游处理策略"

每条依赖链应明确：
- 若上游 FAIL（非 ENV_BLOCKED），下游是跳过还是降级？
- 若上游 BASELINE_INVALID，下游是否继续？

### 建议 2：C1 的"根因"最小交付标准

将 C1 的交付标准从"给出根因"降级为"给出根因假设 + 可证伪实验设计"，不要求在本波内完成修复。这样 C1 的 PASS 条件更现实。

### 建议 3：B2 增加运行时设备检查

在 B2 判据中增加：`运行时至少一个 tensor 的 .device 属性为 cuda/sdaa 类型，或 teico-smi 观测到计算期间 SPE-Util 跃升 >20%`。

### 建议 4：D1 增加环境预检查

在 D1 的 5400 s 预算中，前 600 s 用于环境预检查（`pip install --dry-run` 或 `import` 测试），若失败则快速记录 ENV_BLOCKED，不进入物理计算。

### 建议 5（第四方向）：增加"判例库回流"mission

本提案产出的所有 honest-FAIL 和 BASELINE_INVALID 案例，应自动回流到根因判例库（PB-xxx）。建议增加一条 mission：
- **E1**：将本波所有 FAIL/BASELINE_INVALID 案例的结构化记录写入判例库，格式与现有 PB-001~PB-008 一致。
- 判据：判例库新增条目 ≥3 条，每条包含症状/根因/检查顺序/治愈/勿重蹈五要素。
- 预算：140/5400 s（0 卡）。
- 价值：直接支持 owner 指令"新判例由介入复盘沉淀"。

## 总结

| 方向 | 致命伤 | 判据可裁性 | 预算现实性 | 总体评价 |
