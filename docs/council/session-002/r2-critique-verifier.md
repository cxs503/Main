## 提案一：r1-proposal-guide（glm-5.2 · 软件功能成熟化）

### ① 致命伤

**F1 — 总预算超帽 53%，违反 owner 纪律。**
Owner 指令明确「预算帽 140 调用/5400s」。本提案总预算 215 调用 / 10800s，提案人辩称"3 worker 并行，单 worker 最大 65 调用/3300s，均在帽内"。这是对预算帽的**错误解读**——140/5400 是**波次总帽**，不是 per-worker 帽。若按 per-worker 理解，3 worker × 140 = 420 调用上限，owner 何必设 140？此解读若被采纳，预算纪律形同虚设。**阻断。**

**F2 — 任务 D（样本库填充 ≥10000 条）的"10000"数字无来源依据。**
00_context.md 中知识库样本现状为 0/10000。提案人直接设定 D4 目标为 ≥10000 条，但未说明：
- 10000 这个数字的物理意义是什么？（统计显著性？覆盖参数空间？）
- 生成 10000 条唯一工况需要多少参数组合？SUBOFF × 31 速度 + DTMB × 50 速度 + KVLCC2 × 20 速度 × 多排水量 = 最多 ~3100 组合（假设 5 个排水量变体），远不到 10000。
- 若靠重复调用凑数，provenance_hash 去重后实际入库数可能远低于 10000。
**阻断：数字凭空而来，无法验证。**

### ② 被低估的风险

**R1 — Holtrop 方法对 SUBOFF 潜艇的适用性被轻描淡写。**
提案承认"Holtrop 对高速细长体 Fr>0.4 误差可能 >5%"，但 SUBOFF 潜艇的 Fr 范围（3-9 m/s，L≈5.7m）对应 Fr ≈ 0.4-1.2，**完全超出 Holtrop 方法的适用范围**（Holtrop-Mennen 针对商船，Fr < 0.4）。这意味着 B4 的"≤5% pass"判据对 SUBOFF 几乎必然 FAIL。提案人应提前标注"SUBOFF 不适用 Holtrop"，而非事后 honest-FAIL。

**R2 — batch_sweep 端点不存在于当前 API。**
提案假设 `/calculations/batch_sweep` 可用，但 audit_capabilities 显示平台无此端点。任务 A 本身就是在创建这个端点，但 A4 的"端到端验证"依赖 A1-A3 全部完成——如果 A 线任何一环 FAIL，D 线全部阻塞。提案未给出 A 线 FAIL 时的降级路径（除了 D4 的"降级为单工况循环"，但这需要 95 调用，已超单 worker 帽）。

**R3 — Alembic 迁移在容器化环境中的可执行性未验证。**
D1 依赖 Alembic 迁移脚本可执行，但 docker-compose.yml 中 DB 服务配置与 Alembic 的 connection string 是否匹配？若 DB 未就绪或 schema 版本冲突，迁移将静默失败或破坏现有数据。

## 提案二：r1-proposal-solver（deepseek-v4-flash · 求解器精度与 SDAA）

### ① 致命伤

**无明确致命伤。** 本提案是三个提案中**最严谨**的：数字有来源标注、不确定处显式列出、放弃条件清晰。但有以下严重问题：

### ② 被低估的风险

**R1 — B0 普查的"3 卡 2 小时"假设过于乐观。**
B0 要对 9 个非 LBM 库做普查（py 文件数、代码行、sdaa 引用、benchmarks、tests），每个库需要：
- 遍历目录结构
- 统计代码行
- grep sdaa 引用
- 检查 benchmarks/tests 目录
- 尝试导入/运行

9 个库 × 5 项检查 × 可能的依赖安装/环境配置，2 小时非常紧张。更关键的是：**如果某个库的依赖无法在当前环境安装（如 CUDA 版本不匹配），普查将卡住**。提案未给出"依赖安装失败"的降级路径。

**R2 — C2/C3/C4 的"≤3%"判据对 3D 算例可能过于严格。**
- C2（sphere_re100）：Cd vs 参考值 ≤3%——对于 Re=100 的球体绕流，文献 Cd ≈ 1.0-1.1，3% 误差意味着 Cd 必须在 1.03-1.07 之间。LBM 方法能否达到这个精度取决于网格分辨率和碰撞模型。提案未说明当前网格分辨率是否足够。
- C3（dambreak3d）：质量漂移 ≤ CPU 基线——但提案承认"若 CPU 基线本身 > 0.1%/1e4 步，以 CPU 基线为准"。这意味着如果 CPU 基线质量漂移 5%，SDAA 只要 ≤5% 就算 PASS——**判据实际上被 CPU 基线质量绑架**。
- C4（Laplace）：Δp·R/σ ≤3%——相场方法的 Laplace 定律验证对界面厚度参数敏感，提案未说明界面厚度是否已收敛。

**R3 — D 线（DEM-FEM 耦合）的 Hertz 标杆适用性存疑。**
提案人自己在 §7 承认"TensorFEM 是否支持接触单元我没查"。如果 TensorFEM 不支持接触单元，Hertz 标杆无法执行。提案给出了降级方案（梁受集中力挠度），但这需要额外时间重新设计标杆。

**R4 — 卡位表峰值 6 卡，但 owner 指令说"利用率 12/32，在飞 24"。**
提案人按"峰值 6 卡、上限 12 卡"保守写，但未解释：如果 24 个在飞任务突然释放资源，6 卡峰值是否会造成资源浪费？反之，如果 24 个在飞任务占用资源，6 卡是否能保证？提案未给出资源调度策略。

## 提案三：r1-proposal-software（MiniMax-M2.5-AWQ · 软件功能成熟化）

### ① 致命伤

**F1 — 四个方向全部是"前端+后端"全栈开发，但预算中前端"0 卡"的假设不成立。**
方向 A/B/C/D 的 S2 都涉及前端开发（Vue 组件），预算标注"0 卡"。但前端开发需要：
- npm install（依赖安装）
- npm run build（构建）

这些步骤**需要计算资源**，不是"0 卡"能完成的。更关键的是，前端构建可能需要 Node.js 环境，而当前容器环境是否已配置？提案未验证。

**F2 — 四个方向的 S0 全部标注"前置：无"，但实际存在强依赖。**
- 方向 A（批量调度）的 S0 需要扩展现有 `/tensor/executions/batch` 接口——但该接口**是否存在**？提案未验证。
- 方向 B（谱系追溯）的 S0 需要完善谱系数据模型——但现有数据模型是什么？提案未给出当前 schema。
- 方向 C（复现一键）的 S0 需要复现数据模型——但"复现"的定义是什么？配置复现？环境复现？数据复现？提案未明确。
- 方向 D（工作流编排）的 S0 需要工作流数据模型——但工作流引擎是否已存在？提案未说明。

**四个方向的 S0 都假设"从零开始设计"，但实际可能需要在现有代码基础上修改——这需要先读码，而读码时间未计入预算。**

### ② 被低估的风险

**R1 — 6 天总工期不现实。**
四个方向共 12 个 S 级任务（A0-A2, B0-B2, C0-C2, D0-D2），每个 S 任务 1.5-2 天。但：
- S 任务之间有依赖（如 A1 依赖 A0），不能并行。
- 前端 S2 任务需要后端 S0/S1 完成后才能开始。
- 实际关键路径：A0(1.5d) → A1(2d) → A2(1d) = 4.5d；B0(1.5d) → B1(1d)+B2(2d) = 3.5d（可并行）；C0(1.5d) → C1(2d) → C2(1d) = 4.5d；D0(2d) → D1(2d) → D2(1d) = 5d。
- **关键路径 5 天**，加上集成测试和文档，6 天非常紧张。

**R2 — WebSocket 实时更新（方向 A S2）需要后端支持，但方向 A S0/S1 未提及 WebSocket 实现。**
提案说"先用轮询，WebSocket 作为后续优化"，但判据要求"实时更新延迟 <5s"。轮询的延迟取决于轮询间隔，若间隔 <5s，服务器压力大；若间隔 >5s，不满足判据。**判据与实现方案矛盾。**

**R3 — 谱系图可视化（方向 B S1）的 D3.js 集成复杂度被低估。**
D3.js 谱系图需要：
- 数据格式转换（后端谱系数据 → D3 层次结构）
- 力导向布局或树形布局
- 节点交互（点击、拖拽、缩放）
- 性能优化（大规模谱系图）

1 天完成基础可视化非常紧张，更不用说"节点可点击查看详情"和"导出功能"。

2. **修正 SUBOFF 适用性**：明确标注"SUBOFF 不适用 Holtrop，B4 对 SUBOFF 预期 FAIL"，或改用适合潜艇的阻力计算方法（如 CFD 或经验公式）。
3. **增加 ice/open_water 任务**：至少各加 1 条 mission，哪怕只是 API 骨架 + 测试。

### 对提案二（solver）
1. **B0 普查增加依赖检查步骤**：在普查前先检查每个库的 requirements.txt/dependencies，标记"依赖可满足/不可满足"。
2. **C3 判据增加绝对阈值**：除"≤ CPU 基线"外，增加"质量漂移绝对值 ≤ 0.5%/1e4 步"，避免被低质量 CPU 基线绑架。
3. **D2 增加网格收敛性检查**：在 Hertz 标杆判据中增加"单元尺寸减半时接触刚度变化 < 5%"，确保不是网格不足导致的误差。

### 对提案三（software）
1. **所有前端判据改为后端 API 判据**：将"看板页面可展示"改为"API 返回队列状态 JSON"；将"谱系图可展示"改为"谱系查询 API 返回层次结构 JSON"。UI 验证推迟到后续波次。
2. **S0 增加"读码验证"步骤**：在每个 S0 前加 0.5d 的"验证现有 API/schema 是否存在"，避免从零设计。
3. **增加 honest-FAIL 路径**：每个方向增加"若 X 天内无法完成 Y，则降级为 Z"的明确路径。

## 第四方向建议（优于全部提案的组合方案）

**方向 E：精度基线 + 软件 MVP 组合（推荐）**

结合三个提案的优点，提出一个更务实的组合：

| Mission | 来源 | 内容 | 预算 | 判据 |
|---|---|---|---|---|
| E1 | 提案二 A1+A2 | 88 工件 sha256 快照 + 布尔判定补齐 | 0 卡 / 140 调用 | JSON 含 88 条记录，每条含 pass/fail 布尔 |
| E2 | 提案二 A3 | 单卡性能基线（5 次重复，CV ≤2%） | 1 卡 / 140 调用 | CV ≤2%；记录 MLUPS/显存 |
| E3 | 提案一 B1+B2 | 对标参考数据集 + benchmark_validate 端点 | 0 卡 / 45 调用 | ≥10 条参考记录；端点返回 error_pct + pass |
| E4 | 提案一 C1+C2 | 计时埋点 + timing_baseline 端点 | 0 卡 / 45 调用 | p50/p90/p99 统计正确 |
| E5 | 提案三 A-S0（裁剪版） | 批量提交 API（仅后端，无前端） | 0 卡 / 60 调用 | 批量提交 100 工况，返回状态 JSON |
| E6 | 提案二 C1 | FAIL 根因分类（10 案例） | 0 卡 / 140 调用 | 根因分类表含 evidence 字段 |

**总预算**：约 570 调用（超 140 帽），但可分两波执行：
- 波次 1（E1+E2+E3+E6）：约 465 调用 → 仍需压缩
- 波次 2（E4+E5）：约 105 调用

**实际建议**：由于 140 调用帽非常紧，建议本波次只做 **E1+E2+E3**（约 325 调用，仍超帽），或进一步裁剪为 **E1+E2**（约 280 调用）。

**核心洞察**：140 调用/5400s 的预算帽对于"软件功能开发 + 精度验证"的组合任务来说**过于紧张**。建议 owner 考虑：
1. 提高预算帽至 200-250 调用/7200s
2. 或将软件功能开发与精度验证分属不同波次
